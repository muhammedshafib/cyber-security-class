# 5. Understand Backend Fundamentals

The **backend** is the part of a web application that works behind the scenes. Users normally don't see the backend directly.

A simple web application looks like this:

```text
        User
         ↓
     Frontend
 HTML + CSS + JS
         ↓
    HTTP Request
         ↓
      Backend
         ↓
 ┌───────┴────────┐
 ↓                ↓
API            Database
         ↓
    HTTP Response
         ↓
      Frontend
```

For cybersecurity, understanding the backend is very important because authentication, authorization, databases, sessions, APIs, and business logic are handled mainly on the backend.

---

# 1. APIs

**API = Application Programming Interface**

An API allows different software components to communicate with each other.

For example, a mobile banking application might communicate with a banking server through an API.

```text
Mobile App
    ↓
API Request
    ↓
Backend Server
    ↓
Database
    ↓
API Response
    ↓
Mobile App
```

### Example API request

```http
GET /api/users/10 HTTP/1.1
Host: example.com
```

The backend might return:

```json
{
    "id": 10,
    "name": "Shafi",
    "role": "student"
}
```

This is a common format called **JSON**.

---

## Common API methods

APIs commonly use HTTP methods:

```text
GET     → Read data
POST    → Create/send data
PUT     → Replace data
PATCH   → Update part of data
DELETE  → Delete data
```

Example:

```http
GET /api/products
```

Could return a list of products.

```http
POST /api/products
```

Could create a new product.

### Cybersecurity connection

APIs must properly check:

* Authentication
* Authorization
* Input validation
* Rate limits
* Access control
* Data exposure

For example, simply knowing:

```text
/api/users/10
```

should **not** automatically mean that every user can access user 10's private information.

---

# 2. Databases

A **database** stores application data.

For example, a website might store:

```text
Users
Products
Orders
Messages
Payments
Sessions
```

A simple database table could look like:

| ID | Username | Email                                         |
| -: | -------- | --------------------------------------------- |
|  1 | shafi    | [shafi@example.com](mailto:shafi@example.com) |
|  2 | arjun    | [arjun@example.com](mailto:arjun@example.com) |

---

## Types of databases

Two important categories are:

### Relational databases

Examples:

* MySQL
* PostgreSQL
* SQLite
* Microsoft SQL Server

They commonly use **SQL**.

Example:

```sql
SELECT username FROM users;
```

This asks the database:

> Give me the usernames from the users table.

### NoSQL databases

Examples include:

* MongoDB
* Redis
* Cassandra

They can store data in structures other than traditional relational tables.

---

## Backend + Database

Suppose you log into a website.

The backend may perform something like:

```text
User enters username/password
            ↓
        HTTP Request
            ↓
       Backend Server
            ↓
       Database Query
            ↓
       User information
            ↓
       Authentication check
            ↓
        HTTP Response
```

The browser should **not directly connect to the database**.

Normally:

```text
Browser → Backend → Database
```

not:

```text
Browser → Database
```

---

## Cybersecurity connection

Databases need protection against:

* Unauthorized access
* SQL injection
* Data leakage
* Weak database credentials
* Excessive permissions
* Poor encryption practices

For example, applications should use **parameterized queries/prepared statements** rather than directly concatenating untrusted input into SQL queries.

# 3. Authentication Concepts

**Authentication** means verifying **who a user is**.

A common example is login.

```text
Username: shafi
Password: ********
        ↓
      Login
        ↓
Backend verifies credentials
        ↓
Authentication successful
```

### Authentication vs Authorization

These two concepts are extremely important.

**Authentication:**

> "Who are you?"

**Authorization:**

> "What are you allowed to do?"

Example:

```text
User logs in
    ↓
Authentication
    ↓
"Shafi is a valid user."
    ↓
Authorization
    ↓
"Shafi can view his profile."
```

Being authenticated does **not** automatically mean you have permission to perform every action.

---

## Common authentication methods

### Username + Password

```text
Username
   +
Password
   ↓
Authentication
```

### Multi-Factor Authentication

MFA adds another verification factor.

For example:

```text
Password
   +
Authenticator code
   ↓
Login
```

Other factors can include:

* Security keys
* Authenticator apps
* Biometrics

---

## Password security

A secure application should **not store plain-text passwords**.

Instead, passwords should be processed using password-hashing mechanisms designed for password storage, such as:

* Argon2
* bcrypt
* scrypt

Conceptually:

```text
Password
   ↓
Password hashing
   ↓
Stored password hash
```

During login:

```text
Entered password
       ↓
Verification against stored hash
       ↓
Valid / Invalid
```

# 4. Session Management

After logging in, how does the website remember that you're logged in?

This is where **sessions** come in.

Without some mechanism for maintaining state, every HTTP request would essentially be independent.

A simplified flow:

```text
1. User logs in
       ↓
2. Server verifies credentials
       ↓
3. Server creates a session
       ↓
4. Server sends session identifier
       ↓
5. Browser stores it
       ↓
6. Browser sends it with later requests
```

Example:

```http
Set-Cookie: session_id=abc123
```

The browser may later send:

```http
Cookie: session_id=abc123
```

The server can use that identifier to associate the request with the user's session.

---

## Session example

```text
Login
  ↓
Server creates session
  ↓
Session ID
  ↓
Browser cookie
  ↓
Request to /profile
  ↓
Server checks session
  ↓
Profile returned
```

### Important session security concepts

Secure session management should consider:

* HTTPS
* Secure cookies
* HttpOnly cookies
* SameSite cookies
* Session expiration
* Session invalidation after logout
* Session ID protection
* Session rotation where appropriate

For example:

```http
Set-Cookie: session_id=abc123; Secure; HttpOnly; SameSite=Lax
```

### What these attributes mean

**Secure**

Cookie should only be sent over HTTPS.

**HttpOnly**

Helps prevent JavaScript from directly reading the cookie.

**SameSite**

Controls when cookies are sent in cross-site contexts and can help reduce certain cross-site request risks.

# 5. Web Application Workflows

A **web application workflow** is the sequence of steps that happens when a user performs an action.

Let's understand a login workflow.

### Step 1 — User opens login page

```text
Browser
   ↓
GET /login
   ↓
Backend
   ↓
Login page
```

### Step 2 — User enters credentials

```text
Username
Password
   ↓
Submit
```

### Step 3 — Browser sends request

```http
POST /login HTTP/1.1
Content-Type: application/x-www-form-urlencoded

username=shafi&password=********
```

### Step 4 — Backend processes request

```text
Receive input
     ↓
Validate input
     ↓
Find user
     ↓
Verify password
     ↓
Create session
```

### Step 5 — Server responds

For example:

```http
HTTP/1.1 302 Found
Location: /dashboard
Set-Cookie: session_id=abc123
```

### Step 6 — Browser requests dashboard

```http
GET /dashboard HTTP/1.1
Cookie: session_id=abc123
```

### Step 7 — Backend checks session

```text
Session valid?
     ↓
   Yes
     ↓
Return dashboard
```

# Complete Web Application Flow

Put everything together:

```text
                 USER
                   │
                   ↓
               Frontend
                   │
                   │ HTTP Request
                   ↓
               Backend/API
                   │
          ┌────────┴────────┐
          ↓                 ↓
   Authentication       Business Logic
          │                 │
          └────────┬────────┘
                   ↓
                Database
                   │
                   ↓
             Backend/API
                   │
                   │ HTTP Response
                   ↓
               Frontend
                   │
                   ↓
                 USER
```

# Cybersecurity Perspective

As a cybersecurity student, you should ask questions at each stage.

### API

```text
Who can access this API?
Is authentication required?
Is authorization checked?
```

### Database

```text
Is user input safely handled?
Can unauthorized users access data?
Are database permissions restricted?
```

### Authentication

```text
How are passwords protected?
Is MFA supported?
Are login attempts controlled?
```

### Sessions

```text
How is the session identified?
Does the cookie use Secure/HttpOnly/SameSite appropriately?
Does logout invalidate the session?
```

### Workflow

```text
Can a user skip a step?
Can they access another user's data?
Are permissions checked on every sensitive operation?
```

This way of thinking is important for later cybersecurity topics such as **Burp Suite, API security, authentication vulnerabilities, authorization problems, session security, SQL injection, XSS, and OWASP web application security**.

```text
HTML/CSS/JavaScript
        ↓
     HTTP Request
        ↓
    API / Backend
        ↓
 Authentication
        ↓
 Business Logic
        ↓
     Database
        ↓
    HTTP Response
        ↓
      Browser
```

This is the **basic foundation of web application architecture**.
