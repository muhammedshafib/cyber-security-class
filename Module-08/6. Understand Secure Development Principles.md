# 6. Understand Secure Development Principles

Secure development means **building software in a way that reduces security vulnerabilities from the beginning**.

A simple mindset is:

> **Never blindly trust input, always control what the application accepts, processes, and displays.**

The five concepts are connected:

```text
User Input
    ↓
1. Input Validation
    ↓
Application Processing
    ↓
2. Secure Coding
    ↓
3. Authentication
    ↓
4. Authorization
    ↓
5. Output Handling
    ↓
User
```

---

# 1. Input Validation

## What is input validation?

**Input validation means checking user-provided data before your application uses it.**

Never assume that user input is safe.

For example, a registration form asks:

```text
Username: __________
Age:      __________
Email:    __________
```

A normal user might enter:

```text
Username: John
Age: 22
Email: john@example.com
```

But someone could enter unexpected data.

The application should check:

```text
Is the input present?
Is it the correct type?
Is it within the allowed length?
Is it in the expected format?
Is it within the allowed range?
```

### Example

If age must be between 18 and 100:

```text
18 → Valid
25 → Valid
100 → Valid
5 → Invalid
150 → Invalid
```

### Email

Expected:

```text
john@example.com
```

Obviously invalid examples might be:

```text
hello
abc
```

The application should validate the format.

---

## Why is input validation important?

Without proper validation, attackers may try to send malicious or unexpected input.

For example:

```text
Normal:
username = John

Unexpected:
username = [malicious input]
```

This can contribute to vulnerabilities such as:

* SQL injection
* Command injection
* XSS
* Path traversal
* Logic errors

### Simple rule

> **Treat all external input as untrusted until it has been properly validated.**

---

# 2. Output Handling

Input validation protects the application **when data enters**.

Output handling protects the application **when data leaves or is displayed**.

For example, a website displays a user's comment:

```text
User comment → Database → Backend → Webpage
```

The application shouldn't blindly put that data into an HTML page.

### Example

User enters:

```text
Hello John
```

The website can safely display:

```text
Hello John
```

But if someone enters HTML/JavaScript-like content, the application must ensure it isn't interpreted as executable code when displayed.

This is particularly important for preventing **Cross-Site Scripting (XSS)**.

---

## Encoding

One important output-handling technique is **output encoding**.

Conceptually:

```text
Raw data
   ↓
Encode for the output context
   ↓
Display safely
```

For example, HTML has special characters such as:

```text
<
>
&
"
'
```

When untrusted text is inserted into HTML, appropriate encoding helps ensure it is treated as **text rather than markup/code**.

### Simple rule

> **Never blindly trust data just because it came from your own database.**

Data stored in a database could originally have come from a user.

# 3. Authentication Awareness

You already learned authentication.

### Authentication means:

> **"Who are you?"**

Example:

```text
Username
   +
Password
   ↓
Authentication
   ↓
User identified
```

As a developer, you need to understand that authentication is a security-sensitive part of an application.

### Important practices

#### Passwords

Don't store passwords as plain text:

```text
❌ password123
```

Use a proper password-hashing mechanism such as:

```text
Argon2
bcrypt
scrypt
```

#### Login protection

Applications should consider:

```text
Rate limiting
Account lockout/temporary delays where appropriate
Multi-factor authentication
Secure password recovery
Secure session handling
```

#### HTTPS

Login credentials and authentication information should be protected during transmission using HTTPS.

---

## Authentication question

Whenever you create a protected feature, ask:

> **"How does the application know who this user is?"**

---

# 4. Authorization Awareness

Authentication and authorization are different.

### Authentication

> **Who are you?**

### Authorization

> **What are you allowed to do?**

Example:

```text
User A → Logged in
```

Authentication says:

```text
✓ User A is authenticated
```

But authorization asks:

```text
Can User A delete another user's account?
```

Maybe the answer is:

```text
❌ No
```

An administrator might have:

```text
✓ View users
✓ Edit users
✓ Delete users
```

while a normal user might have:

```text
✓ View own profile
✓ Edit own profile
✗ Delete other users
```

---

## Important security idea

Never rely only on the frontend for authorization.

For example, hiding a button:

```html
<button style="display:none">
    Delete User
</button>
```

does **not** provide real security.

An attacker might directly send a request to the backend.

The backend must check:

```text
Request
  ↓
Is user authenticated?
  ↓
Is user authorized for this action?
  ↓
YES → Continue
NO  → Reject
```

### Simple rule

> **The server must enforce authorization.**

---

# 5. Secure Coding Mindset

This is the most important part.

A secure coding mindset means:

> **Think about how your code could fail or be misused before assuming that everything will work normally.**

Instead of thinking only:

```text
"What happens when a normal user uses my application?"
```

also think:

```text
"What happens if someone sends unexpected input?"
"What if they modify a request?"
"What if they aren't authorized?"
"What if the database is unavailable?"
"What if a value is missing?"
"What if someone sends the request directly?"
"What sensitive information could be exposed?"
```

---

# Example: Normal Developer Mindset

Suppose you're creating:

```text
Delete Account
```

Normal thinking:

```text
User clicks Delete
       ↓
Account deleted
```

Secure thinking:

```text
User clicks Delete
       ↓
Is the user authenticated?
       ↓
Is this actually their account?
       ↓
Is the request valid?
       ↓
Does the server authorize the action?
       ↓
Perform deletion safely
       ↓
Return appropriate response
```

---

# Another Example: File Upload

Suppose your website allows users to upload files.

Normal thinking:

```text
Choose file
 ↓
Upload
```

Secure thinking:

```text
File upload
   ↓
Is the user authenticated?
   ↓
Is the file type allowed?
   ↓
Is the file size allowed?
   ↓
Is the filename safe?
   ↓
Is the storage location safe?
   ↓
Can the uploaded file be executed?
   ↓
Store safely
```

That's the **secure coding mindset**.

# 🧠 Easy Way to Remember

| Principle                 | Simple question                         |
| ------------------------- | --------------------------------------- |
| **Input validation**      | Is this input acceptable?               |
| **Output handling**       | Can I display this data safely?         |
| **Authentication**        | Who is this user?                       |
| **Authorization**         | What can this user do?                  |
| **Secure coding mindset** | How could this code be misused or fail? |

### One-line definitions

**1. Input validation** → Check data before trusting/using it.

**2. Output handling** → Safely handle data before displaying or sending it.

**3. Authentication awareness** → Understand how the application verifies user identity.

**4. Authorization awareness** → Understand and enforce what each user is allowed to access or perform.

**5. Secure coding mindset** → Always think about security, unexpected input, misuse, failure, and data exposure while developing.

# 🛠️ Practical: Apply All 5

For your cybersecurity learning, build a small **secure user-management application**.

### Features

```text
1. Register
2. Login
3. Logout
4. View profile
5. Edit profile
6. Delete profile
```

Then apply each principle:

### 1. Input validation

Test:

```text
Empty username
Very long username
Invalid email
Invalid age
Unexpected characters
```

### 2. Output handling

Test whether user-provided text is displayed safely rather than interpreted as HTML/JavaScript.

### 3. Authentication

Test:

```text
Can an unauthenticated user access /profile?
```

Expected:

```text
❌ Access denied
```

### 4. Authorization

Create two users:

```text
User A
User B
```

Then verify:

```text
User A → Can access own profile ✓
User A → Cannot modify User B's profile ✗
```

### 5. Secure coding mindset

Review the whole application and ask:

```text
Where do I trust user input?
Where is authentication checked?
Where is authorization checked?
Where is sensitive data handled?
What happens when something fails?
Could error messages reveal sensitive information?
```

This practical will connect your **HTML/CSS → HTTP → APIs → backend → database → authentication → sessions → security** knowledge into one workflow.
