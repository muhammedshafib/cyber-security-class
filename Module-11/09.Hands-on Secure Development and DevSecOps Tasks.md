# **9. Apply Through Hands-on Tasks**

This section is about applying everything you learned in Secure SDLC, Secure Coding, Application Security Testing, CI/CD, and AI-Assisted Secure Development to practical projects.

The goal is to become capable of reviewing an application's security, identifying weaknesses, assessing risks, and preparing professional security assessment reports.

This is an important step toward becoming an **Application Security Engineer / DevSecOps Engineer**, and it also builds useful skills for your offensive security career.

## **1. Review Application Architectures**

**Meaning:**

Application architecture review means examining how an application is designed, how its components communicate, and whether its design follows security principles.

**What you need to review:**

1. Frontend architecture.
2. Backend architecture.
3. Database architecture.
4. Authentication and authorization.
5. API communication.
6. Network security.
7. Data storage and encryption.

**Practical example**

Imagine an application with this architecture:

**Frontend**

React application

HTTPS requests

**Backend**

Python Flask API

**Database**

MySQL

**Your task:**

Review this architecture and identify:

- Is HTTPS implemented?
- Is authentication secure?
- Is database access protected?
- Are API endpoints properly authorized?
- Are sensitive credentials exposed?

**Expected result:** An architecture security review containing identified weaknesses and recommended improvements.

## **2. Analyze Security Weaknesses**

**Meaning:**

Identify vulnerabilities, insecure configurations, and weaknesses that could allow attackers to compromise an application.

**Important areas:**

| Area               | What to analyze                                 |
| ------------------ | ----------------------------------------------- |
| Authentication     | Weak passwords, login weaknesses                |
| Authorization      | Broken access control                           |
| Input validation   | SQL Injection, XSS                              |
| API security       | Missing authentication, excessive data exposure |
| Database           | Weak permissions, insecure storage              |
| Configuration      | Debug mode, exposed secrets                     |
| Session management | Insecure cookies, session weaknesses            |

**Practical task:**

Use a deliberately vulnerable application in your own lab.

Recommended practice platforms:

- OWASP Juice Shop
- DVWA
- OWASP WebGoat

Your workflow:

1. Identify the application components.
2. Explore the application's attack surface.
3. Perform authorized security testing.
4. Identify vulnerabilities.
5. Determine severity.
6. Recommend security fixes.
7. Retest after remediation.

**Expected result:** A vulnerability assessment report.

## **3. Assess Software Supply Chain Risks**

**Meaning:**

Software supply chain security means protecting all the components, libraries, dependencies, tools, and services used to build an application.

For example, your Python application may use:

- Flask
- Requests
- SQLAlchemy
- PyJWT
- Other third-party packages

If one dependency contains a known vulnerability, your application could also become vulnerable.

**What you need to check:**

1. Vulnerable third-party dependencies.
2. Outdated packages.
3. Malicious or compromised packages.
4. Exposed API keys and secrets.
5. Dependency integrity.
6. Untrusted software sources.

**Practical tools:**

| Tool       | Purpose                                          |
| ---------- | ------------------------------------------------ |
| pip-audit  | Detect vulnerable Python dependencies            |
| Safety     | Python dependency security analysis              |
| Dependabot | Identify dependency vulnerabilities on GitHub    |
| Trivy      | Scan dependencies, containers and configurations |
| Gitleaks   | Detect exposed secrets in repositories           |

**Hands-on commands**

Install pip-audit:

```
pip install pip-audit
```

Scan dependencies:

```
pip-audit
```

Check installed Python packages:

```
pip list
```

Check your project dependencies:

```
pip freeze > requirements.txt
```

**Expected result:** A software dependency security report showing vulnerable packages and recommended updates.

## **4. Design Secure Development Workflows**

**Meaning:**

A secure development workflow is a process that integrates security checks into every stage of software development, from writing code to deploying the application.

This is where Secure SDLC and DevSecOps work together.

**Example: Secure CI/CD pipeline**

1. **Developer writes code**

   VS Code and Python
2. **Push code to GitHub**

   Git and GitHub repository
3. **Run automated tests**

   Pytest
4. **Perform security scanning**

   Bandit, pip-audit, Gitleaks
5. **Build the application**

   GitHub Actions
6. **Deploy securely**

   Deployment after required checks pass

**Your task:**

Design a CI/CD workflow that automatically performs:

1. Code quality checks.
2. Unit testing.
3. Dependency vulnerability scanning.
4. Secret detection.
5. Static Application Security Testing (SAST).
6. Build and deployment checks.

**Example GitHub Actions workflow**

Create this file:

`.github/workflows/security.yml`

```
name: Secure Development Pipeline

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  security:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: |
          pip install -r requirements.txt
          pip install pytest bandit pip-audit

      - name: Run tests
        run: pytest -v

      - name: Run Bandit
        run: bandit -r .

      - name: Audit dependencies
        run: pip-audit
```

This is a starter security pipeline. It runs tests, performs Python security analysis, and audits dependencies. A production pipeline should additionally configure secret scanning, pinned action versions, permissions, and deployment protections.

**Expected result:** A working GitHub Actions pipeline that automatically checks your application whenever code is pushed or a pull request is created.

## **5. Create DevSecOps Assessment Reports**

**Meaning:**

A DevSecOps assessment report is a professional document that explains the security condition of a software development process, identifies weaknesses, evaluates risks, and recommends improvements.

This is an important professional skill because security engineers must communicate their findings clearly to developers, management, and security teams.

**What your report should contain:**

| Section                     | Details                             |
| --------------------------- | ----------------------------------- |
| 1. Executive summary        | Overall security condition          |
| 2. Scope                    | Application and components reviewed |
| 3. Architecture review      | Security design findings            |
| 4. Vulnerability assessment | Identified weaknesses               |
| 5. Supply chain assessment  | Dependency and package risks        |
| 6. CI/CD assessment         | Pipeline security findings          |
| 7. Risk assessment          | Severity and impact                 |
| 8. Recommendations          | Suggested fixes                     |
| 9. Retesting                | Verification of fixes               |
| 10. Conclusion              | Final security assessment           |

### **Example vulnerability report**

| Finding                  | Severity | Recommendation                   |
| ------------------------ | -------- | -------------------------------- |
| SQL Injection            | Critical | Use parameterized queries        |
| Outdated dependency      | High     | Update vulnerable package        |
| Hardcoded API key        | High     | Remove secret and rotate it      |
| Missing security headers | Medium   | Configure appropriate headers    |
| Debug mode enabled       | Medium   | Disable debug mode in production |

### **Example report finding**

**Finding: Hardcoded API Key**

- Vulnerability: API key stored directly in source code.
- Risk: Unauthorized users could obtain the key.
- Impact: Unauthorized access to connected services.
- Severity: High, depending on the key's privileges and exposure.
- Recommendation: Store secrets in environment variables or an appropriate secrets manager.
- Verification: Confirm the key is removed, rotated, and not exposed in repository history.

**Expected result:** A professional DevSecOps assessment report with evidence, severity ratings, remediation steps, and retesting results.
